# Windows portable updates — implementation status

## Available

- Windows native-only metadata checks against `Miku0139oao/rta-sales-client-go` latest stable release. Web RPC remains an explicit allowlist and does not expose update methods.
- Settings display build version, manual checks and **更新日誌 / Changelog** as escaped, collapsible text (220px scroll region). The changelog identifies the latest official GitHub Release's actual version, including equal or older releases; it is not labelled as the installed version. Empty bodies and check failures are shown honestly in Settings. Startup metadata checking defaults on, can be disabled using the existing settings storage key, and never downloads an executable. Startup errors are non-disruptive.
- `Client.Inspect` returns latest stable release version/body separately from an optional validated newer install candidate, using the same single bounded 2 MiB metadata request. `Client.Check` retains its candidate-only contract. Desktop `changelogVersion` / `changelogBody` are independent of `candidateId`, `availableVersion` and candidate `releaseNotes`; equal/older releases cannot authorize installation. Draft/prerelease metadata is rejected, and newer releases must still pass all asset validation. No Markdown HTML is interpreted.
- The App-level update component remains mounted across navigation. Its Settings details and Settings page share a centered 960px column; compact notices on other pages retain their existing placement.
- Backend candidates retain exact repository/tag asset URLs. UI APIs accept no download URLs, paths or hashes. Version comparison is numeric; unknown/development/prerelease versions cannot update.
- HTTP timeouts, size bounds, HTTPS-only allowlisted redirects, exact portable/checksum asset names, unique SHA256 entries and downloaded size/hash verification are covered by isolated tests. Downloads occur only through the explicitly confirmed native install API; metadata checks never download.
- Pure publisher/image verification policy and helper transaction orchestration support injected tests. Trust must hold for both current and candidate executables, and publisher subjects must match exactly. Leaf certificate renewal is allowed when the subject remains unchanged. PE image/hash/type/architecture and signed version checks are separate mandatory checks.
- Windows portable-only build, version injection, resource/config agreement and checksum generation after signing of the exact output. NSIS is not required; WebView2 must be installed manually.
- Release CI only creates new unsigned **drafts**. It never modifies historical releases. Explicit local signed publication verifies tag, commit, version, current clean checkout, signatures/publisher, hashes and downloaded draft copies before draft-to-public transition.

## Confirmed native installation and work ownership

`InstallUpdate({candidateId, confirmed:true})` is now wired to the Windows staging/helper adapter. The Go-only `ConfigureNativeUpdateLifecycle` hook configures the installer and Wails `app.Quit` before `app.Run`. `installSupported` is true only for Windows amd64 with a stable injected build version matching the trusted current executable's signed numeric version. Development, unsigned, mismatched and unsupported builds expose a reason instead of a download button. Trust is rechecked at installation time; startup capability is not an authorization shortcut.

- The backend snapshots its immutable candidate; requests supply no URLs, paths, hashes or executable versions. Missing consent, stale candidates, concurrent checks/installs and unsupported capability are rejected before downloading.
- Installation atomically reserves exclusivity under `operationMu`. Every public work entry (including dialogs, scans, profile/catalog operations, reads and writes) holds a counted admission through its return. Nested entries do not hold mutexes through work and cannot deadlock. Separate existing operation flags keep account/workbook work and sales-analysis supplements protected after the primary RPC returns. Runtime inspection and cancellation are deliberately not new-work admissions.
- A random native export lease spans PDF/AI rendering, folder selection and **all** writes; frontend `finally` releases it on success, cancellation or failure. Leases do not expire mid-export. Web export bypasses native leases; direct web update/lease calls reject unsupported and remain absent from the web RPC allowlist.
- The app-level notice persists through navigation. Checks are metadata-only; a separate modal explicitly warns about closure, restart and unsaved report/preview loss before download. Accounts/settings and old executable backups are preserved. Progress is honest stage text, not invented byte percentages. Busy work disables the action and the backend independently enforces admission.
- Before commit, cancellation only cancels the worker context; the reservation remains until cleanup confirms helper exit. Uncertain helper exit leaves the gate reserved and shows **keep the app open and retry cancellation**. A cancellation retry cannot return success merely because the input pipe was already closed.
- Once readiness is received, the transition to `committing` closes cancellation atomically. Commit and quit execute outside all app/update mutexes. The parent only quits after an authenticated **commit-accepted ACK**, not after merely writing a commit frame. Missing, invalid or late acknowledgements fail without quitting and trigger helper cleanup; uncertain exit still retains exclusivity. Committed shutdown retains exclusivity; `ServiceShutdown` cancels owned work contexts without cancelling the committed helper. No force termination or elevation occurs.

A controlled signed **0.4.6 → 0.4.7 fixture pair** passed the real Wails update flow: explicit UI confirmation, normal parent exit, authenticated helper commit, process-handle wait, verified replacement, restart at the same path, and helper exit. The new executable SHA256 matched the signed candidate, retained `previous.exe` matched the original, and nondefault WebView settings/localStorage plus synthetic profile bytes survived. Both test executables used real Authenticode signing and the production helper entrypoint and verification policy.

Only GitHub HTTP responses were fixture-backed. The `portable_update_smoke` build tag selects isolated synthetic accounts, a separate single-instance ID/WebView directory and fixture transport; these overrides are absent from production. Reproduce with `pwsh -NoProfile -File scripts/test-portable-update-native.ps1` (requires local signing and launches only sandbox fixtures). No real account or installed application was accessed. This does not test historical v0.4.5 auto-updating (it has no updater), real GitHub availability, or every machine's revocation cache/network policy.

For unsupported builds, finish work and close the app before manually updating at the **same path and basename** (WebView settings depend on the executable basename); retain the old executable as a backup. Never force termination or overwrite a running executable.

## Implemented Windows adapter semantics

- `WindowsIdentityVerifier` uses `WinVerifyTrustEx` and obtains the primary signer certificate from the **verified provider chain**. Publisher comparison uses the full X.500 subject, not a name hardcoded in the app or any-valid-publisher policy. Version comes from `VS_FIXEDFILEINFO` only after trust succeeds: matching product/file versions, zero fourth component, and no debug/prerelease/private/special-build flags.
- Trust is noninteractive and uses cached-only revocation/chain retrieval. Missing revocation cache can fail closed even for a legitimate signature. The updater does not weaken policy to work around offline failures.
- `NewWindowsStaging()` derives the exact current executable and cwd internally. It creates a unique adjacent `.rta-update-*` directory with a protected DACL granting full access only to the current user and SYSTEM, copies the trusted current image as `helper.exe`, and records volume/file IDs. Downloads are explicit immutable backend candidates. Staging, helper, `previous.exe` and `result.json` are retained; `Close()` releases handles, not files.
- Ancestor directory handles deny deletion/rename; reparse directories/files, hard-linked executable files, remote shares, alternate streams and ambiguous paths are rejected. Files must remain on the same local volume. Filesystems without the required ACL/identity semantics fail closed.
- The executable and pinned ancestry must also have safe owners and effective DACLs. Only the current user, SYSTEM, Administrators and Windows TrustedInstaller are trusted owners/writers. Other principals may read/execute but may not write bytes, delete children, change metadata, take ownership or rewrite DACLs. The immediate target parent must additionally deny them file/subdirectory creation. Null/unsupported ACLs fail closed; broad dangerous allow ACEs are rejected even when a deny ACE might counteract them. Inheritance-only ACEs are checked on actual children rather than treated as effective parent permissions. **Shared/public writable installation directories are unsupported**; use a private user-owned folder. The updater never repairs ACLs or elevates.
- Trust/version checks hold read handles denying write/delete. Since path-based Windows version APIs do not promise delete sharing, those handles are then closed and new `READ | DELETE` handles acquired; **both file IDs and hashes are checked again**. Each rename uses `SetFileInformationByHandle(FileRenameInfo)` on that very DELETE-owning handle. Denying third-party delete sharing does not prohibit the handle's own rename; this behavior is exercised on Windows, not assumed.
- `StartHelper(ctx)` rechecks helper/current bytes and current trust before launching only the private copy. Configuration and a random 256-bit receipt token travel over inherited anonymous pipes; no command-line paths or web RPC exist. The helper validates configuration, parent image path, PID **creation time**, private directory identity and files before returning authenticated readiness. Readiness and the helper's independent commit-receipt lifetime are each bounded to 30 seconds; the parent's commit-accepted ACK wait is bounded to five seconds, and parent-handle wait to two minutes. The helper has a three-minute context budget; synchronous Windows APIs are not forcibly interrupted, so this is not a hard process-lifetime deadline. Parent readiness timeout still fails without quitting the app, and expired helper context prevents entering the backup/replace phase. Once the good file has moved to backup, completion/recovery is intentionally not interrupted by cancellation. Cancellation sends a private frame; no process is terminated or elevated.
- `HelperSession.Commit()` retains the response pipe and requires the exact token-authenticated `commit-accepted` frame before reporting success. The helper rechecks its readiness deadline after reading commit, then acknowledges acceptance before waiting. Expiry with still-open pipes, EOF/exit, bad tokens and missing ACKs cannot authorize parent quit. A failed commit is one-shot, closes the response reader and requests cancellation; cleanup still waits for actual helper exit. After an ACK, the lifecycle owner quits normally **outside mutexes**. The helper waits on an actual `SYNCHRONIZE` process handle, never PID polling or pipe EOF.
- After parent exit, trust/hash/version are reverified immediately before the two individual same-volume atomic renames. The target's basename and cwd are preserved. Windows tests show that a deny-delete read open cannot overlap the existing DELETE-access rename handle. Before that handle is closed, the safe owner/DACL boundary is therefore revalidated; this prevents a different unprivileged principal from substituting the path during the necessary close/reopen interval. The reopened read-only handle denies writes/deletion, and file ID, PE/hash, trusted publisher and signed version are rechecked. **That read lock stays held through actual `CreateProcess`**, whose compatibility is tested on Windows. The identical policy applies to rollback launches, using the verified recovery copy's recorded file ID and original signed version. A successful `CreateProcess` is the commit point; later application crashes are not automatically rolled back.
- On replacement/launch failure, rollback copies from the still-locked old backup into a private recovery file, verifies the copy, and atomically restores it. **The good backup is never consumed.** Unexpected recreation or identity change at the target causes recovery to stop rather than overwrite an unrelated file. Fault diagnostics are flushed to `result.json`; failure to retain diagnostics is reported.

### Threat and recovery boundary

This protects against malicious remote release bytes/metadata, ordinary file-lock/path races and launch-path substitution by other unprivileged principals: installations granting them unsafe file/parent/ancestor access are rejected, rather than relying on private staging alone. It does not defend against privileged administrators/SYSTEM/Windows servicing or another malicious process already running as the same user that can rewrite ACLs or patch the process. Directory handles share write access; the additional owner/DACL policy, not those handles alone, excludes other principals' metadata/ACL mutation. Final launch and rollback use checked paths under a loader-compatible deny-write/delete read lock. The sequence is **not a power-loss-atomic transaction**: a crash between the two renames can leave the target absent and the good private backup retained for manual recovery. No automatic cleanup deletes that backup.

Windows sandbox tests compile a small credential-free dummy executable and run only temporary private copies. They cover Unicode paths, real parent waits/timeouts, locks, tampering, rename collisions, actual CreateProcess failure, rollback and backup retention. Real Windows ACL tests grant Everyone dangerous rights on disposable fixtures and verify rejection; owner/group risks additionally have SID/permission-model tests (no other user account is created or impersonated). Updated and rollback launches both attempt writes/deletion/substitution under the held read lock and then successfully CreateProcess the dummy. The actual dispatch's shared I/O implementation exercises JSON parsing, Windows preparation, authenticated ACK, independently expired readiness with writable pipes, queued deadline races, helper exit and concurrent cancellation; only unsigned dummy identity policy is injected. A directory junction test exercises real reparse rejection without a shell or elevation. The copied package test binary separately exercises the public helper dispatch's unsigned rejection. These fault tests complement the positive signed desktop fixture upgrade above. For read-only positive trust testing, set `RTA_UPDATE_TRUST_FIXTURE` to a canonical Windows path to an existing signed release; the file is never launched or modified.

## Signed publication

From a clean checkout at an existing, matching stable tag and existing draft. First replace the CI placeholder title and notes with curated release information and screenshot links. Publication rejects placeholders and preserves the draft title, notes and screenshots:

```powershell
./scripts/publish-portable.ps1 -Tag vX.Y.Z -Commit <full-40-character-commit> -PublisherReference <previous-trusted-portable.exe>
```

This is an explicit publishing operation, not part of normal development verification. Do not run it for a preview or this implementation task. Never change historical release assets. Signing configuration remains local; do not include credentials or personal publisher names in release notes.
